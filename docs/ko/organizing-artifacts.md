# 아티팩트 정리와 작성 이력

[English](../organizing-artifacts.md) | 한국어

<!-- 번역 기준: 2026-10-30 영문 organizing-artifacts.md 동시 작성본 -->

이 문서는 다음 릴리스를 위해 구현한 기능을 설명합니다. 배포된 0.16.1에는 포함되지 않습니다. 이 변경 사항이 포함된 빌드에서 아래 절차를 진행하세요.

스크린샷은 격리된 공개 모드 서버에서 가상 데이터와 관리자 계정으로 영어 UI를 촬영했습니다. 예시 모델 이름은 테스트용 표시이며, 운영 환경에서 사용한 모델을 뜻하지 않습니다.

컬렉션과 카테고리는 용도가 다릅니다. 컬렉션은 관련 아티팩트를 섹션과 목차가 있는 한 페이지로 보여 줍니다. 카테고리는 아티팩트 자체를 바꾸지 않고 목록을 정리합니다. 작성 이력에는 각 버전을 만든 도구, 모델, 사용자를 기록합니다.

## 컬렉션 페이지 만들기

![섹션 목차와 아티팩트 본문을 함께 표시하는 컬렉션 페이지](../assets/screenshots/manual-collection.png)

컬렉션 뷰어는 참조한 아티팩트 옆에 목차를 표시합니다. 사용자마다 열람 권한이 있는 항목만 보입니다.

컬렉션은 기존 아티팩트를 참조하며, 내용을 복사하지 않습니다. 같은 아티팩트를 여러 컬렉션에 넣을 수 있습니다.

1. 탐색 메뉴에서 **New collection**을 선택하세요.
2. 제목, 태그, 공개 범위를 입력하고 Markdown으로 소개를 작성하세요.
3. **Add section**을 선택하고 섹션 제목을 입력하세요.
4. **Add artifact**에서 아티팩트를 선택하세요. 목록에 없다면 **Artifact ID**에 ID를 붙여 넣을 수 있으며, 서버는 접근 권한을 확인합니다. **Version**과 **Display**를 설정하세요.
5. **Move up**, **Move down**, **Remove**로 섹션과 항목을 정리하세요.
6. 컬렉션을 생성한 뒤 소개, 섹션, **Contents** 목차가 의도대로 표시되는지 확인하세요.

![섹션 순서, 아티팩트 참조, 버전, 표시 방식을 설정하는 컬렉션 편집기](../assets/screenshots/manual-collection-editor.png)

화면은 최신 버전을 따라가며 본문을 표시하는 참조입니다. 같은 설정에서 버전을 고정하거나 링크 카드를 선택할 수 있습니다.

기존 컬렉션을 열고 **Edit**를 선택하면 구성을 바꿀 수 있습니다. 편집을 마치면 **Save version**을 선택하세요. 작성 중인 내용은 자동 저장되지 않습니다. 컬렉션 안에 넣은 다른 컬렉션은 재귀적으로 펼치지 않고 카드로 표시합니다. 없거나 보관되었거나 접근할 수 없는 참조의 내용은 표시하지 않습니다. 기존 참조 중 사용할 수 없는 항목이 있으면 편집 화면에서 제외하고 경고를 표시합니다. 이 참조를 유지하려면 접근 권한 또는 참조한 아티팩트·버전을 복구하세요. 제거하려면 **I understand that saving removes unavailable references from the new version**을 선택하고 저장하세요. 해당 참조를 뺀 새 버전이 생기며, 이전 버전은 유지됩니다. 확인 없이 저장하면 요청을 거부합니다.

HTTP와 MCP 업데이트에서는 명시적 불리언 값인 `dropUnavailableReferences: true`로 같은 복구 작업을 수행합니다. 읽기 결과의 항목 수가 줄었다고 이 값을 자동으로 설정하지 마세요. 관리자 복구에는 별도의 확인이 있으며, 기존 복구 규칙에 따라 선택한 과거 버전을 변경합니다. 일반적인 새 버전 저장과는 다른 작업입니다.

컬렉션 하나에는 최대 50개 섹션과 200개 참조를 넣을 수 있습니다. 소개는 최대 50,000자, 섹션 제목은 최대 200자까지 지원합니다.

각 참조의 표시 방식을 선택하세요.

| 설정 | 동작 |
| --- | --- |
| 최신 버전 | 컬렉션을 읽을 때 참조 대상의 최신 버전을 표시합니다. |
| 버전 고정 | 지정한 버전 번호를 유지합니다. 릴리스 보고서나 매뉴얼에 적합합니다. |
| 본문 표시 | 참조한 아티팩트를 컬렉션 페이지 안에 표시합니다. |
| 카드 | 참조한 아티팩트로 이동하는 링크를 표시합니다. |

컬렉션 자체의 버전을 고정해도 **최신 버전**으로 지정한 참조까지 고정되지는 않습니다. 페이지 전체를 같은 상태로 재현해야 한다면 포함된 아티팩트의 버전도 각각 고정하세요. 관리자의 버전 정리로 참조한 버전이 삭제되면 다른 버전으로 임의 대체하지 않습니다.

컬렉션을 편집하면 다른 아티팩트처럼 새 버전이 생깁니다. 컬렉션에도 기존 아티팩트 공유 기능을 사용합니다.

### 컬렉션의 열람 권한

컬렉션을 볼 수 있다고 해서 참조한 아티팩트의 권한까지 생기지는 않습니다. Artifacty는 항목마다 열람 권한을 확인하고, 접근할 수 없는 항목을 제외합니다. 필터링된 컬렉션을 읽을 때 해당 항목의 제목, 내용, 식별자를 노출하지 않습니다. 따라서 같은 컬렉션도 사용자마다 보이는 항목이 다를 수 있습니다.

컬렉션의 공유 링크는 컬렉션에만 접근을 허용합니다. 포함된 모든 아티팩트의 공유 링크로 작동하지 않습니다. 서버 모드, 계정 권한, IP 제한도 유지됩니다. 허용 IP 대역 밖의 공유 링크 예외를 사용해도 참조한 아티팩트까지 공개되지는 않습니다.

![익명 사용자의 컬렉션 접근 가능 여부를 확인하는 미리보기](../assets/screenshots/manual-collection-sharing.png)

이 예시에서는 익명 사용자가 컬렉션과 참조 세 개를 모두 볼 수 있습니다. 결과는 테스트 데이터와 현재 권한을 기준으로 합니다.

**Sharing**의 **Collection audience preview**에서 **Recipient**를 선택하고 **Check access**를 누르세요. 미리보기에는 접근 가능한 참조 수와 수신자의 컬렉션 열람 가능 여부가 나옵니다. 이 작업은 권한을 부여하지 않습니다.

실제 수신자 계정으로 컬렉션을 확인하세요. 소유자나 관리자는 수신자보다 더 많은 항목을 볼 수 있습니다. 비공개 아티팩트의 제목이나 민감한 내용을 컬렉션 소개 또는 섹션 제목에 직접 쓰지 마세요. 이 텍스트는 컬렉션 자체의 내용이므로 컬렉션의 공유 권한을 따릅니다.

## 개인·팀 카테고리 사용

![개인·팀 카테고리 소속과 펼쳐진 팀 카테고리 생성 설정](../assets/screenshots/manual-categories.png)

같은 아티팩트가 개인 카테고리와 팀 카테고리에 하나씩 속해 있습니다. 펼쳐진 생성 설정에서는 기존 팀을 선택할 수 있습니다.

카테고리를 사용하려면 활성 계정으로 로그인해야 합니다. 익명 사용자나 브라우저 로컬 설정으로 계정을 대신하지 않습니다. 카테고리 관리에는 JavaScript가 필요합니다.

1. 탐색 메뉴에서 **Categories**를 여세요.
2. **Create category**에서 이름을 입력하고 **Personal** 또는 **Team**을 선택하세요. 팀 카테고리라면 사용 가능한 팀을 선택한 뒤 생성하세요.
3. 아티팩트를 열고 **Categories** 링크로 이동하세요. 원하는 카테고리의 **Included**를 선택하면 소속이 즉시 적용됩니다. **Saved** 표시를 확인하세요.
4. **Artifacts**로 돌아가 **Category** 필터를 선택하거나 카테고리의 아티팩트 수 링크를 눌러 소속 항목을 확인하세요.
5. 이름을 바꾸려면 이름을 편집하고 입력창 밖으로 이동한 뒤 **Saved**를 확인하세요. 카테고리를 지우려면 **Delete category**를 선택하고 확인하세요. 아티팩트는 남습니다.

![개인 Research library 카테고리로 좁힌 아티팩트 목록](../assets/screenshots/manual-category-filter.png)

카테고리를 선택하면 읽을 수 있는 소속 항목만 표시합니다. 아티팩트의 태그나 접근 권한은 바뀌지 않습니다.

카테고리는 기존 팀을 사용합니다. 페이지에는 사용할 수 있는 팀이 표시됩니다. 관리자는 **Manage teams and members**에서 접근 설정으로 이동할 수 있습니다. 일반 사용자는 관리자에게 팀 구성원 변경을 요청하세요.

- 개인 카테고리는 만든 사용자에게 속합니다. 관리자를 포함한 다른 사용자는 카테고리 기능을 통해 접근할 수 없습니다.
- 팀 카테고리는 해당 팀의 현재 구성원과 관리자가 사용합니다. 현재 구성원이나 관리자라면 누구나 관리할 수 있습니다.
- 하나의 아티팩트를 여러 카테고리에 넣을 수 있습니다. 카테고리에 추가해도 태그, 내용, 소유자, 공유 권한은 바뀌지 않습니다.
- 팀 구성원도 각 아티팩트의 열람 권한이 있어야 합니다. 항목 수와 필터 결과에서는 접근할 수 없는 아티팩트를 제외합니다. 보관된 항목은 보기를 통해 포함하지 않는 한 제외합니다.
- 카테고리에서 항목을 빼도 아티팩트는 남습니다. 카테고리를 삭제하면 분류 정보만 사라지고 아티팩트는 삭제되지 않습니다.

이름은 앞뒤 공백을 제거한 뒤 1~120자여야 합니다. 같은 개인 또는 팀 범위에서 이름은 고유해야 합니다. 중복 확인에서는 ASCII 영문 대소문자를 구분하지 않으며, 전체 유니코드 대소문자 변환은 적용하지 않습니다. 개인 또는 팀 범위마다 최대 200개의 카테고리를 만들 수 있습니다. 생성 후에는 카테고리의 범위를 바꿀 수 없습니다. 다른 대상과 공유하려면 별도의 카테고리를 만드세요.

저장된 보기는 검색 조건을 저장하고, 카테고리는 직접 선택한 아티팩트의 소속을 저장합니다. 작업 대상을 직접 골라 모으려면 카테고리를, 검색 조건에 따라 결과가 바뀌어야 한다면 저장된 보기를 사용하세요.

## 작성 이력 확인

![최초 작성자는 Claude Code로 유지하고 이후 버전의 Codex 작성 정보를 표시하는 화면](../assets/screenshots/manual-provenance.png)

선택한 v2에는 Codex가 기록되어 있고 최초 작성자는 Claude Code로 남아 있습니다. 두 모델 이름은 모두 테스트용 가상 이름입니다.

아티팩트를 열고 **Version author**를 펼치세요. **Original author**와 선택한 버전의 도구, 제공사, 모델, 계정 ID, 출처를 확인하세요. 이전 버전을 선택하면 해당 버전의 작성 정보를 볼 수 있습니다.

Artifacty는 모든 이름을 하나의 에이전트 값으로 처리하지 않고 작성 정보를 나누어 기록합니다.

| 필드 | 의미 |
| --- | --- |
| `tool` | `claude-code`, `codex`, `cursor`와 같은 작성 클라이언트입니다. |
| `provider` | 제공된 경우 기록하는 모델 제공사입니다. |
| `model` | 클라이언트가 제공한 실제 모델 식별자입니다. |
| `userId` | 인증된 요청 또는 신뢰하는 로컬 감사 컨텍스트에서 가져온 사용자 식별자입니다. |
| `rawSourceAgent` | 해석에 참고할 수 있도록 보존한 원래 출처 이름입니다. |
| `source` | 작성 정보의 출처로 `legacy`, `mcp-client`, `self-reported`, `unknown` 중 하나입니다. |
| `toolSource` | 작성 도구를 확인한 경로입니다. |
| `modelSource` | `self-reported` 또는 `unknown`입니다. |

`artifact.createdBy`에는 최초 작성자가 남습니다. `artifact.provenance`는 최신 버전의 작성 정보이며, `artifact.versions`의 각 항목에도 자체 `provenance`가 있습니다. 이전 버전을 확인할 때는 아티팩트의 최신 정보 대신 해당 버전의 작성 정보를 확인하세요.

도구가 명확한 별칭은 통일합니다. **Claude Code**는 `claude-code`, **Gemini CLI**는 `gemini-cli`, **codex-cli**는 `codex`가 됩니다. **Claude**, **GPT**, **OpenAI**, **Anthropic**, **Google**, **Gemini**만으로는 특정 작성 도구를 식별하지 않습니다. 제공사나 모델을 모르면 `null`로 남기며, 클라이언트 이름으로 모델을 추정하지 않습니다.

stdio MCP 연결은 `initialize`에서 클라이언트 이름을 전달할 수 있습니다. 이는 클라이언트의 선언이며 실제 소프트웨어의 신원을 검증한 증거는 아닙니다. 클라이언트가 보낸 모델 정보도 자체 신고한 값입니다. HTTP MCP는 상태를 유지하지 않으므로 이전 `initialize`의 클라이언트 이름을 이후 요청에 보존하지 않습니다. 작성 이력은 작업을 추적하기 위한 정보이며, 모델의 진위를 증명하는 기능은 아닙니다.

기존 데이터의 작성 정보에는 레거시 출처임을 표시합니다. 이전 Artifacty 릴리스는 Claude Code를 Claude로 합치는 등 일부 이름을 통합했습니다. 그 과정에서 이미 사라진 정보는 마이그레이션으로 복구할 수 없습니다.

## MCP로 컬렉션 생성

먼저 호출자가 읽을 수 있는 아티팩트의 ID를 확인하세요. 아래 `report-artifact-id`는 `artifacty_list` 또는 `artifacty_create`에서 받은 실제 ID로 바꾸세요.

다음 인수로 `artifacty_collection_create`를 호출합니다.

```json
{
  "title": "Release review",
  "description": "Evidence and decisions for the release.",
  "sections": [
    {
      "id": "evidence",
      "title": "Evidence",
      "items": [
        {
          "artifactId": "report-artifact-id",
          "version": 1,
          "display": "inline"
        }
      ]
    }
  ],
  "provenance": {
    "tool": "codex",
    "provider": "openai",
    "model": "actual-model-id"
  }
}
```

모델 식별자는 실제 실행 환경에서 확인한 값을 사용하세요. 모르면 생략하고, 예시 문자열 `actual-model-id`를 실제 모델 이름으로 보내지 마세요.

`artifacty_get`으로 결과를 읽습니다. 편집하려면 반환된 `id`, 마지막으로 읽은 `expectedVersion`, 변경한 소개와 전체 섹션 목록을 `artifacty_collection_update`에 전달하세요. 버전이 오래되었으면 다른 편집을 덮어쓰는 대신 충돌을 반환합니다. 사용할 수 없게 된 참조가 있다면 접근 권한을 복구하거나, 제외될 항목을 검토한 뒤 의도적으로 `dropUnavailableReferences: true`를 사용하세요. 새로운 버전을 따라가는 참조는 `version: "latest"`로 지정합니다.

기본 아티팩트의 형식과 유형은 모두 `collection`입니다. 콘텐츠에는 `description`과 `sections`가 있는 JSON 객체가 들어가고, 제목과 작성 정보는 아티팩트 필드로 유지됩니다. 이력, 접근 권한, 공유에는 일반 아티팩트 API를 사용합니다. [MCP 참조](mcp-public-api.md)와 [아티팩트 스키마](artifact-schema-v1.md)를 참고하세요.

## HTTP와 CLI 작성 정보

HTTP 생성·업데이트 요청 본문에도 같은 `provenance: { tool, provider, model }` 객체를 전달합니다. 이 객체를 `metadata` 안에 넣지 마세요. 자유 형식 메타데이터는 공식 작성 기록이 아닙니다.

CLI의 publish, import, update에는 `--tool`, `--provider`, `--model`을 사용합니다.

```sh
artifacty publish --title "Review notes" --content "# Review notes" --format markdown --tool codex --provider openai
```

이 예시는 실행 중인 모델 ID를 알 수 없으므로 모델을 생략했습니다. 실제 값을 알고 있을 때만 `--model`을 추가하세요.

카테고리 HTTP 경로는 `GET`/`POST /api/categories`, `PATCH`/`DELETE /api/categories/{id}`, `PUT`/`DELETE /api/categories/{id}/artifacts/{artifactId}`입니다. `GET /api/category-teams`는 카테고리를 만들 수 있는 팀 목록을 반환합니다. 개인 카테고리는 `{ "name": "My references", "scope": "personal" }`로 생성합니다. 팀 카테고리에는 `"scope": "team"`과 선택한 `teamId`도 필요합니다. 아티팩트 목록은 `categoryId`를 받으며, MCP의 `artifacty_list`에도 사용할 수 있습니다. API 토큰 범위와 현재 사용자의 권한을 모두 적용합니다.

## 저장소 마이그레이션

이 빌드는 저장소 스키마 11을 사용하며, 공개 아티팩트 레코드의 스키마 버전은 1로 유지됩니다. 기존 저장소를 열 때는 일반 업그레이드 절차에 따라 검증된 스냅샷을 만든 뒤 마이그레이션합니다. 이전 바이너리는 새 저장소를 열지 못합니다. 전체 저장소 JSON 백업에는 카테고리와 소속 정보도 포함됩니다. 빌드를 바꾸기 전에 스냅샷을 보존하고, 이전 빌드로 돌아가야 한다면 [복구 절차](upgrade-backups.md)를 따르세요. 샘플 매뉴얼을 다시 설치해도 사용자가 편집한 내용이나 이미 설치된 매뉴얼 버전을 덮어쓰지 않습니다.

## 결과 확인

1. 컬렉션을 열고 목차를 따라 이동하세요. 섹션 순서와 표시된 항목이 편집한 내용과 일치하는지 확인합니다.
2. 임시 저장소에서 참조한 아티팩트를 수정하세요. 최신 참조는 바뀌고 고정 참조는 지정한 버전을 유지하는지 확인합니다.
3. 실제 수신자 계정으로 컬렉션을 여세요. 제한된 항목이 보이지 않고, 컬렉션 공유만으로 추가 접근 권한이 생기지 않았는지 확인합니다.
4. 카테고리를 선택하고 읽을 수 있는 소속 아티팩트만 보이는지 확인하세요. 소속을 제거한 뒤에도 기본 목록에 아티팩트가 남아 있는지 확인합니다.
5. 서로 다른 작성 도구 정보를 사용해 아티팩트를 만들고 수정하세요. 최초 작성자는 유지되고 새 버전에는 별도의 작성 정보가 기록되는지 확인합니다.
