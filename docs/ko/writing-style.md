# 문서 작성 스타일

Artifacty의 영어와 한국어 문서는 ASD-STE100의 명료성 원칙을 따릅니다. 완전한 문장과 일관된 용어를 사용하고, 적용 조건을 분명히 밝힙니다. 다만 언어와 독자에 맞게 유연하게 적용하며, ASD-STE100을 준수한다고 주장하지는 않습니다.

앞서 정한 ‘75%’ 목표는 편집 방향을 뜻하며, 표준 준수율이 아닙니다. 문장을 짧게 만들거나 정해진 어휘에 맞추기 위해 정확한 의미를 희생하지 마세요.

## 영어 문서의 문장과 용어

- 문장마다 핵심 내용을 분명히 밝히세요. 조건이나 예외를 따로 떼면 뜻이 모호해지는 경우에는 서로 연결해서 설명하세요.
- 책임을 구분해야 할 때는 관리자, 아티팩트 소유자, 사용자, 서버 등 주체를 밝히세요. 문맥상 분명한 주어는 반복하지 않아도 됩니다.
- 능동태를 우선 사용하세요. 주체를 알 수 없거나 중요하지 않으면 수동태를 사용하세요.
- 같은 개념에는 같은 용어를 사용하세요. UI 이름, API 필드, CLI 명령어를 정확히 맞추세요.
- artifact, MCP, webhook, CIDR 등 정착된 용어를 유지하세요. 익숙하지 않은 용어는 처음 사용할 때 설명하세요.
- 무엇이 달라지고, 누가 행동하며, 언제 규칙이 적용되는지 알 수 있도록 완전한 문장으로 설명하세요.
- 고정된 단어 수 제한을 강제하지 마세요. 제한된 사전에 맞추기 위해 정확한 용어를 바꾸지 마세요.

## 지시와 동작 설명

- 행동을 설명하기 전에 전제 조건과 적용 조건을 밝히세요.
- 번호가 있는 각 단계에는 하나의 주요 행동을 담으세요. 필요한 명령어나 UI 요소를 제시하고, 행동과 밀접하게 연결된 확인 절차는 함께 설명해도 됩니다.
- 독자가 성공 여부를 판단해야 한다면 예상 결과와 확인 방법을 함께 알려 주세요.
- 기본값, 권한, 예외, 실패 시 동작, 복구 요건을 빠뜨리지 마세요. 문장을 줄이기 위해 이 정보를 생략해서는 안 됩니다.
- 필수 사항과 권장 사항을 구분하세요. 명세에 나오는 MUST, SHOULD, MAY의 의미를 유지하세요.
- 설명문을 편집할 때 명령어, 식별자, URL, 예제 값, 기술적 제약을 유지하세요. 예제가 현재 구현과 다르다면 실제 동작을 확인한 뒤 고치세요.
- 설계 제안과 과거의 결정은 현재 동작과 구분하세요. 계획 중인 기능을 현재 릴리스에서 지원하는 것처럼 설명하지 마세요.

## 문서 유형에 따른 적용

설치 안내, API 참조, 보안 문서에는 이 규칙을 가장 엄격하게 적용하세요. README 소개, 설계 근거, 출시 글에서는 문장이 자연스럽게 이어지도록 설명해도 됩니다. 독자에게 필요한 설명은 유지하세요. 조건이나 예외를 생략한다면 짧은 글도 도움이 되지 않습니다.

영어 문서에서는 다음과 같이 씁니다.

> By default, share links do not work in private mode. An administrator must enable them in Access settings.

이 예문은 ‘비공개 모드에서는 기본적으로 공유 링크가 동작하지 않으며, 관리자가 접근 설정에서 활성화해야 한다’는 뜻입니다. 기본값, 책임 주체, 설정 위치를 명시합니다.

표준의 목적과 구성은 [공식 ASD-STE100 소개](https://www.asd-ste100.org/about.html)를 참고하세요.

## 필수 문서 작업 절차

1. 명령어, 옵션명, 기본값, 권한, 한도, 응답 필드를 현재 구현과 대조하세요. 배포된 동작, 아직 배포하지 않은 저장소 변경, 제안을 구분하세요. 과거 설계 문서만으로 현재 동작을 판단하지 마세요.
2. 영문·한국어 안내를 함께 수정하고, 문서 목차와 관련 샘플 매뉴얼에도 반영하세요. 샘플 소스를 수정해도 사용자 저장소에 이미 설치된 매뉴얼은 교체되지 않습니다.
3. 문서에서 안내하는 브라우저 기능마다 해당 단계 옆에 실제 영어 UI 스크린샷과 설명을 넣으세요. 개요 이미지 몇 장으로 기능별 화면을 대신하지 마세요. 필요한 조작부를 펼치거나 이해에 도움이 되는 예시 값을 입력한 상태로 촬영하세요. 별도의 임시 저장소에 예시 데이터를 준비하세요. 운영 아티팩트, 인증 정보, 개인정보, 실제 접근 토큰을 촬영하지 마세요.
4. 글꼴과 다이어그램 등 비동기 콘텐츠가 모두 표시된 뒤 촬영하세요. 각 이미지를 직접 열어 라벨, 가독성, 잘림, 로딩 오류, 민감정보 노출을 확인하세요. 계정이나 접근 모드에 따라 버튼이 달라진다면 촬영 조건도 밝히세요. 두 언어 문서에서 이미지는 공유하고, 설명과 대체 텍스트는 번역하세요.
5. 스크린샷은 `docs/assets/screenshots/`에 저장하세요. 상대 링크와 npm 패키지 포함 여부를 확인하세요. 실제로 없는 버튼이나 동작을 보여 주도록 이미지를 수정하지 마세요.
6. `npm run docs:check`로 로컬 Markdown 링크, 절 앵커, 문서·이미지의 패키지 포함 여부를 검사하세요. 이 명령은 외부 URL이나 명령어 동작을 검증하지 않습니다. 바꾼 명령은 임시 저장소와 임시 클라이언트 설정 경로에서 별도로 실행하세요. 셸 문법 검사만으로 실행에 성공했다고 판단하지 마세요.
7. 완료를 보고하기 전에 관련 동작 테스트, `npm run lint`, `npm test`를 실행하세요. 릴리스 전에는 `npm run release:check`도 실행하세요. 브라우저 안내는 실행 중인 앱에서 확인하세요. 삭제·복원, 외부 메일 발송, 운영 배포는 격리된 테스트 데이터나 안전한 미리보기로 검증하고, 실행하지 않은 작업은 기록하세요.
8. 변경 파일, 확인한 동작, 스크린샷 위치, 테스트 결과, 남은 검증 한계를 보고하세요. 자동 검사 통과만으로 모든 문서에 오류가 없다고 주장하지 마세요.

## 한국어 문서 작성 기준

한국어에도 STE-100의 명료성 원칙과 fluent-korean 지침을 함께 적용합니다. 두 기준이 충돌하면 **기술적 의미의 정확성 → 자연스러운 한국어 → 문장 길이와 형식 규칙** 순으로 판단합니다. 영어 어순이나 단어 수 제한을 그대로 적용하지 않습니다.

- 문장마다 핵심 내용을 분명히 밝힙니다. 조건과 결과, 원인과 예외가 밀접하게 연결되어 있다면 한 문장으로 설명해도 됩니다.
- 의미를 이해하는 데 필요한 주체와 대상을 생략하지 않습니다. 권한이나 책임을 구분할 때는 주체를 밝히되, 문맥상 분명한 주어는 반복하지 않습니다.
- 조사와 어미를 갖춘 완전한 문장으로 씁니다. 제목과 표에서는 간결한 명사구를 사용할 수 있지만, 설명문을 메모처럼 압축하지 않습니다.
- 조건과 전제를 먼저 설명한 뒤 행동을 안내합니다. 절차에는 필요한 확인 방법과 예상 결과를 함께 적습니다.
- 번역투, 불필요한 수동 표현, 명사 나열을 줄입니다. ‘설정의 변경이 가능합니다’보다 ‘설정을 변경할 수 있습니다’로 씁니다. 수동 표현이 의미를 더 정확하게 전달한다면 유지합니다.
- 같은 개념에는 같은 용어를 사용합니다. UI 이름은 해당 언어의 실제 표기와 맞추고, 명령어·API 필드·코드 식별자는 바꾸지 않습니다. 정착된 번역어가 없다면 원어를 유지하고 필요한 설명을 덧붙입니다.
- 생소한 비유나 긴 대시로 관계를 압축하지 않습니다. 문맥에 맞는 접속사나 별도 문장으로 원인, 조건, 대조 관계를 설명합니다.
- 기본값, 예외, 제한, 복구 조건을 빠뜨리지 않습니다. ‘반드시 해야 합니다’, ‘권장합니다’, ‘할 수 있습니다’를 구분해 의무의 강도를 보존합니다.
- 설명은 ‘합니다’체로 쓰고, 절차는 ‘선택하세요’, ‘실행하세요’처럼 안내합니다. 코드, 식별자, 인용문, 로그와 라이선스 원문에는 문체 규칙을 기계적으로 적용하지 않습니다.

예를 들어 다음과 같이 씁니다.

> 비공개 모드에서는 기본적으로 공유 링크를 사용할 수 없습니다. 관리자가 접근 설정에서 공유 링크를 허용해야 합니다.

문장을 나눌 때는 적용 조건이 달라지지 않는지 확인합니다. ‘백업 검증에 성공하면 서버를 중지하고 복구를 시작하세요’에서 검증 조건을 빼고 행동만 남겨서는 안 됩니다. 자연스러운 문장과 기술적 정확성을 함께 유지하는 것이 목표입니다.
