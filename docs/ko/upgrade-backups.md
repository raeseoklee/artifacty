# 업그레이드 스냅샷과 복구

Artifacty는 기존 저장소를 새 스키마로 마이그레이션하기 전에 로컬 스냅샷을 생성합니다. 이 스냅샷은 필수입니다. 스냅샷 생성이나 검증에 실패하면 마이그레이션 전에 작업을 중단합니다.

저장소의 원래 상태를 복구할 때는 업그레이드 스냅샷을 사용하세요. 다른 환경으로 옮길 수 있는 JSON 백업과 저장소 이전에는 `artifacty backup`과 `artifacty export`를 사용하세요. 두 백업 방식은 별개입니다. `artifacty restore <id>`는 보관한 아티팩트를 복원하는 명령이며, 저장소 스냅샷을 복원하지 않습니다.

## 애플리케이션 자체 업데이트

애플리케이션 업데이트 도구와 스키마 마이그레이션 스냅샷은 목적이 다릅니다. 아티팩트 ID 없이 `artifacty update`를 실행하면 애플리케이션을 업데이트합니다. `artifacty upgrade`도 같은 명령입니다. `artifacty update <id>`는 기존과 같이 아티팩트를 수정합니다.

### 릴리스 확인과 선택

예시의 `<version>`, `<id>`, `/path/to/store`는 실행 전에 정확한 릴리스 버전, 스냅샷 ID, 저장소 경로로 바꾸세요.

```bash
artifacty update --check
artifacty upgrade --check --target-version "<version>" --home /path/to/store
```

`--check`는 설치, 서비스, 저장소를 변경하지 않고 릴리스를 확인합니다. 다른 CLI 플랫폼에서도 사용할 수 있으며, 자동 설치 지원 여부도 표시합니다. 릴리스를 조회하려면 네트워크에 연결되어 있어야 합니다. 관리 대상 서비스를 업데이트할 때는 해당 서비스가 사용하는 패키지 버전을 비교합니다. 명령어를 실행한 CLI 버전만으로 판단하지 않습니다. `--target-version`에는 정확한 버전을 지정합니다. 이 옵션이 없으면 최신 릴리스를 선택합니다. `--home`으로 보호할 저장소를 지정합니다. 자동 다운그레이드는 지원하지 않습니다. 이전 버전을 명시적으로 지정하면 거부합니다. `latest`가 설치된 버전보다 낮으면 현재의 더 최신 버전을 그대로 유지합니다.

설치된 버전이 0.14.0 이전이라면 다음 명령어로 업데이트 도구를 시작하세요.

```bash
npx --yes artifacty@latest update --home /path/to/store && export PATH="$HOME/.local/bin:$PATH"
```

이 명령어는 POSIX Linux 셸 문법을 사용합니다. 업데이트가 성공하면 현재 세션에서 `PATH`의 앞에 `~/.local/bin`을 둡니다. 이후 세션에서도 사용하려면 셸의 `PATH`에 해당 디렉터리를 추가하세요.

업데이트 도구를 사용하려면 `latest` 태그가 0.14.0 이상을 가리켜야 합니다.

### 브라우저에서 업데이트

관리자 계정으로 브라우저에 로그인하세요. **관리 → 서버 업데이트**(`/admin/update`)를 여세요. 이 경로에서는 API 토큰으로 브라우저 세션을 대신할 수 없습니다.

1. **업데이트 확인**을 선택하세요. 서비스를 설치하거나 다시 시작하지 않고 npm의 최신 릴리스를 조회합니다.
2. 브라우저 업데이트를 지원하고 새 버전이 있으면 표시된 대상 버전을 검토하세요.
3. 백업과 재시작에 동의하는 확인란을 선택하세요.
4. **백업 후 업데이트**를 선택하세요.
5. 서버가 다시 시작되는 동안 화면을 열어 두세요. 재연결 후 업데이트 결과를 확인하세요.

업데이트 확인 정보는 10분 후 만료됩니다. 버전을 조회한 브라우저 세션에서만 이 정보를 사용할 수 있습니다. 만료되거나 설치된 버전이 바뀌면 다시 확인하세요. 폼 요청의 출처(origin)는 서버와 정확히 같아야 합니다. 비밀번호를 다시 입력할 필요는 없습니다.

브라우저에서 업데이트를 설치하려면 현재 서버가 root가 아닌 사용자 계정의 Linux systemd 사용자 서비스로 실행되고 있어야 합니다. 다른 설치 환경에서도 최신 릴리스를 조회할 수 있지만 이 화면에서 업데이트를 시작할 수는 없습니다. 업데이트 작업 프로세스는 독립적인 systemd 임시 서비스로 실행되므로 Artifacty 서버를 중지해도 업데이트 작업은 계속됩니다. 상태는 아티팩트 저장소 밖의 `~/.local/share/artifacty/update-jobs`에 보관합니다.

화면을 열거나 상태를 조회하는 것만으로 npm에 접속하거나 패키지를 설치하지 않습니다. 상태를 조회할 때는 작업 프로세스가 중지되었는지 확인하기 위해 systemd를 조회할 수 있습니다. Artifacty가 작업 시작 여부를 확인할 수 없으면 해당 작업의 예약을 유지합니다. 작업 프로세스가 중단되었거나 복구가 끝나지 않았다면 성공으로 처리하지 않습니다. 다음 업데이트 전에 수동으로 상태를 확인해야 합니다. 복구를 검증할 때까지 남아 있는 스냅샷과 릴리스를 보존하세요.

### 자동 설치의 지원 범위

자동 설치와 재시작은 Linux의 systemd 사용자 서비스 `com.artifacty.server`를 지원합니다. 서비스를 실행하는 사용자로 업데이트 도구를 실행하세요. 유닛은 Artifacty 설치 도구가 생성하는 단순한 `ExecStart` 형식을 사용해야 합니다. 선택한 저장소의 `--home`도 명시해야 합니다. 지원하지 않는 명령어 확장이나 따옴표 형식이 있으면 서비스를 중지하기 전에 업데이트를 중단합니다. 자동 업데이트는 root 실행을 거부합니다. root 소유의 전역 패키지를 교체하려고 root로 실행하지 마세요.

업데이트 도구는 `~/.local/share/artifacty/releases`에 패키지를 준비합니다. systemd 드롭인 설정으로 관리 대상 서비스의 실행 파일을 변경하며, 기존 인자와 환경 변수는 유지합니다. 사용자 소유 실행 스크립트는 `~/.local/bin`에 둡니다. 이 디렉터리가 `PATH`에 없으면 스크립트를 사용하기 전에 추가하세요. 기존에 있던 관리 대상이 아닌 파일은 덮어쓰지 않습니다. 기존 root 소유 전역 패키지는 변경하지 않습니다. `PATH`에서 다른 명령어를 먼저 찾는다면 결과에 제공한 절대 경로 `nextCommand`를 사용하세요. 셸 설정은 자동으로 변경하지 않습니다.

macOS, Windows, 포그라운드 서버, 분리된 백그라운드 서버, 임의의 서비스 유닛은 자동 전환을 지원하지 않습니다. 이러한 환경에서는 수동 설치와 스냅샷 절차를 사용하세요.

### 저장소 보호와 롤백

업데이트 전에 같은 저장소를 사용하는 다른 HTTP 서버와 로컬 MCP 클라이언트를 중지하세요. 지원하는 systemd 서비스는 업데이트 도구가 직접 관리합니다. 저장소를 열고 있는 다른 모든 프로세스를 찾을 수는 없습니다. 업데이트 중에는 서비스를 사용할 수 없습니다. 저장소를 롤백하면 스냅샷 이후에 기록한 변경 사항은 사라집니다. 이 절차를 진행하는 동안 다른 쓰기 작업을 실행하지 마세요.

업데이트 도구는 실행 중인 서비스를 중지하기 전에 상태를 확인합니다. 바인드 주소나 IP 정책 때문에 확인할 수 없으면 서비스를 중지하기 전에 업데이트를 거부합니다. 지원하지 않는 서비스 설정도 중지 전에 오류로 처리합니다.

업데이트 도구는 지정한 정확한 버전의 패키지를 준비 디렉터리에 설치하고 검증합니다. 그다음 관리 대상 서비스를 중지하고, 코드를 전환하기 전에 스냅샷을 생성하고 검증합니다. 서비스가 실행 중이었다면 전환 후에 다시 시작하고 상태와 PID를 확인합니다. 중지 상태였던 서비스는 중지 상태를 유지합니다. 롤백에 필요한 이전 코드와 서비스 설정도 보존합니다. 전환이나 재시작에 실패하면 변경한 코드, 서비스 설정, 저장소를 복원한 뒤 이전 서비스를 다시 시작하는 롤백을 시도합니다. 서비스 중지에 실패하면 서비스가 저장소에 계속 기록할 수 있으므로 저장소를 복원하지 않습니다. 복원된 저장소에는 스냅샷 시점의 인증 정보와 보안 상태가 포함됩니다. 클라이언트의 재접속을 허용하기 전에 복구 오류를 확인하세요.

전환 중에 프로세스나 호스트가 갑자기 종료되면 `update.lock`이 남거나 서비스가 중지 상태로 남을 수 있습니다. 다음 업데이트는 무조건 재시도하지 않고 잠금 상태를 보고합니다. 스냅샷, 준비한 릴리스, 복구 파일을 보존하세요. 수동으로 다시 시도하기 전에 서비스와 복구 상태를 확인하세요. 자동 롤백은 처리 가능한 오류에 대응하며, 전원 장애나 강제 프로세스 종료 후의 복구를 보장하지 않습니다.

다시 시작한 서비스가 정상 동작할 때까지 스냅샷과 업데이트 결과를 보관하세요. 자동 롤백을 완료하지 못하면 명시적인 오류를 반환하고 `backupId`를 남깁니다. 해당 스냅샷으로 아래 복구 절차를 진행하세요. 복구 파일을 삭제하거나, 지원하지 않는 스키마를 이전 빌드로 강제로 열지 마세요.

## 스냅샷을 생성하는 시점

- **스키마 마이그레이션:** 기존 저장소를 마이그레이션하기 전에 항상 스냅샷을 생성합니다. 기존 `index.json` 방식의 저장소도 포함합니다. 새로 만든 빈 저장소에는 스냅샷이 필요하지 않습니다.
- **애플리케이션 업데이트:** `ARTIFACTY_BACKUP_ON_UPDATE=true`로 설정하면 애플리케이션 버전이 바뀔 때도 기존 저장소의 스냅샷을 생성합니다. 기본값은 비활성화입니다.
- **애플리케이션 버전을 알 수 없는 경우:** 업데이트 설정을 활성화한 상태에서 애플리케이션 버전 기록이 없는 기존 저장소를 처음 열면 기준 스냅샷을 생성합니다. 이 스냅샷의 원본 애플리케이션 버전은 알 수 없습니다. 이후 같은 버전으로 열 때는 다시 생성하지 않습니다.
- **복원:** 저장소를 교체하기 전에 현재 상태의 복구 스냅샷을 생성하고 검증합니다.

업그레이드하거나 복원하기 전에 해당 저장소를 사용하는 HTTP 서버와 MCP 프로세스를 모두 중지하세요. 서비스, 포그라운드 서버, 로컬 stdio MCP 클라이언트도 포함합니다. Artifacty는 관리 대상 서버의 PID 기록을 확인하지만, 이 기록만으로 저장소를 열고 있는 모든 프로세스를 찾을 수는 없습니다.

스냅샷은 `ARTIFACTY_HOME/upgrade-backups/<id>/`에 저장합니다. 기본 홈 디렉터리는 `~/.artifacty`입니다.

## 스냅샷에 포함되는 내용

각 스냅샷에는 파일 크기와 SHA-256 해시를 기록한 매니페스트가 있습니다. 다음 항목도 포함합니다.

- 모든 테이블과 보안 상태를 포함한, 일관성이 유지되는 원본 SQLite 데이터베이스
- 데이터베이스 또는 기준으로 사용하는 기존 인덱스가 참조하는 모든 버전 파일
- 기존 `index.json` 파일이 있으면 해당 파일

검증 과정에서는 파일 해시, SQLite 무결성, 버전 파일 참조를 확인합니다. 관련 없는 파일, 프로세스 기록, 로그, 전체 설치 디렉터리는 스냅샷에 포함하지 않습니다. 스냅샷에는 인증 정보와 보안 기록이 있으므로 비공개로 보관하세요.

`ARTIFACTY_UPGRADE_BACKUP_KEEP`으로 자동 스냅샷 보관 개수를 지정합니다. 기본값은 `3`이며, `1`부터 `1000`까지의 정수를 사용할 수 있습니다. 업그레이드가 성공하면 오래된 자동 스키마·업데이트 스냅샷을 정리합니다. 이 설정으로 수동 스냅샷이나 복구 스냅샷을 정리하지는 않습니다.

## 스냅샷 확인

저장소를 열거나 마이그레이션하지 않고 스냅샷 목록을 조회하세요.

```bash
artifacty backups list --home /path/to/store
```

출력에서 `id`를 복사하세요. 해당 스냅샷을 검증하세요.

```bash
artifacty backups verify "<id>" --home /path/to/store
```

검증이 성공하면 응답에 `valid: true`가 포함됩니다. 목록 조회는 매니페스트만 확인하므로 전체 검증을 대신할 수 없습니다. 저장소를 체크아웃한 환경에서는 `artifacty` 대신 `node src/cli.js`를 사용하세요.

## 스냅샷 복원

복원하면 현재 데이터베이스, 버전 파일, 기존 인덱스를 교체합니다. 스냅샷 이후의 변경 사항은 더 이상 현재 상태에 반영되지 않습니다. 복원 직전의 상태는 별도의 복구 스냅샷에 보관합니다.

**보안 상태도 이전 상태로 돌아갑니다.** 이전 비밀번호, 권한, 네트워크 규칙, 세션, API 토큰, 공유 링크 기록이 다시 현재 상태가 될 수 있습니다. 스냅샷 이후에 폐기한 세션, 토큰, 링크도 아직 만료되지 않았다면 다시 유효해질 수 있습니다. 사용자의 재접속을 허용하기 전에 복원된 보안 상태를 검토하세요.

1. 이 저장소를 사용하는 서버, 서비스, MCP 프로세스를 모두 중지하세요.
2. `backups list`에서 스냅샷을 선택하세요.
3. `backups verify`로 검증하세요.
4. 명시적인 확인 옵션을 넣어 복원하세요.

```bash
artifacty backups restore "<id>" --confirm restore-store --home /path/to/store
```

5. 응답의 `recoveryBackupId`를 저장하세요.
6. 클라이언트를 다시 연결하기 전에 복원된 보안 설정을 검토하세요.

복원 작업은 선택한 스냅샷을 마이그레이션하지 않습니다. 현재 애플리케이션으로 열면 보호 절차를 거치는 마이그레이션이 다시 시작될 수 있습니다. 복원된 스키마를 지원하지 않는 빌드는 저장소를 열지 않습니다.

## 현재 저장소가 손상된 경우의 복구

Artifacty가 현재 저장소를 검증하지 못해 복구 스냅샷을 만들 수 없으면 `RECOVERY_BACKUP_FAILED`를 반환합니다. 손상된 저장소를 덮어쓰지 않습니다.

1. 손상된 홈 디렉터리와 그 안의 스냅샷을 그대로 보존하세요.
2. 새 빈 홈 디렉터리를 만드세요.
3. 선택한 스냅샷 디렉터리를 새 홈의 `upgrade-backups/` 디렉터리에 복사하세요. 원래 스냅샷 ID와 디렉터리 내용을 유지하세요.
4. `backups verify <id> --home /path/to/new-home`을 실행하세요.
5. `backups restore <id> --confirm restore-store --home /path/to/new-home`을 실행하세요.
6. 새 홈을 사용하기 전에 복원된 데이터와 보안 설정을 검토하세요.

손상된 데이터베이스를 새 홈에 복사하지 마세요. 선택한 스냅샷이 데이터베이스와 참조하는 버전 파일을 제공합니다.

## 중단된 복원 작업의 복구

`.restore-<uuid>` 디렉터리가 남아 있으면 `RESTORE_INCOMPLETE` 오류로 작업을 중단합니다.

1. 해당 디렉터리와 영향을 받은 홈 디렉터리 전체를 보존하세요.
2. `.restore-<uuid>/restore.json`을 읽으세요.
3. `recoveryBackupId`를 찾으세요. 이 ID는 중단된 복원 작업을 시작하기 직전 상태의 스냅샷을 가리킵니다.
4. 해당 복구 스냅샷을 새 빈 홈의 `upgrade-backups/` 디렉터리에 복사하세요.
5. 위 명령어로 새 홈에서 검증하고 복원하세요.

검사를 우회하려고 중단된 복원 디렉터리를 삭제하지 마세요. 이 디렉터리에는 복구에 필요한 증거가 있으며, 이전 데이터베이스와 파일도 들어 있을 수 있습니다.
